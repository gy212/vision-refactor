# 规则检出修复计划（v5 之后）

> 2026-10-17 起草，待用户审阅。依据：甲方第一批样本（71 对，`D:\VisionSamples\2026-10-16_client_batch1\`）的分析报告（本地 `outputs/sample_analysis/report.md`，未入库），以及对 `core/evaluation`、`core/live`、`core/recording` 源码的核对。本文只是计划：每一步都是设计文档 §11.2 中的一个待决策项（D-18～D-23），经用户批准后单独提 PR、单独重新生成受影响的 golden，不和其它改动混在一起。
>
> 摆拳、勾拳的规则和其它缺失的规则另见两个 issue，不在本文范围内。

## 一、要解决的问题

分析结论（详见报告第四、五节）：

1. **录像变速（新发现，最先修）**：录像按名义 30 fps 写文件，但实际每秒只写入 8～20 帧（多数 12～15），回放快了 1.5～3.7 倍。所有以秒为单位的规则参数都因此失真。
2. **单视角检出被融合挡掉**：C15（出拳过高）、C17、C18（不翻胯）、C20 在一个视角已经判出问题，融合后成了"证据不足"。
3. **推定正确的样本大面积误报**：`stance_elbow`、`stance_height` 在 A、B 上 25/25 报警；`stance_knee`、`stance_width`、`stance_toes`、`foot_flexed` 的逐视角误报率在 58%～100%。
4. **动作阶段找不到**：C 类 21 段单拳只有 10 段在任一视角找到动作；鞭腿常因正侧检出次数不同，整段对齐失败。
5. **侧面机位**：侧面摄像头在考生左后方，左式下拍到的主要是后背，右肘、右腕的有效帧只有 3%～21%。

单纯调阈值解决不了以上任何一项。第 1、5 项是录制与拍摄条件，第 2、4 项是判定逻辑，第 3 项是测量方式。

## 三、各步骤

### 步骤 0：录像按真实时间写入（D-18）

**现象**：71 段录像的真实时长（`segment_id` 中的开始时间到 `result.json` 的 `created_at`）是视频时长的 1.5～3.7 倍。

**原因**：
- `core/live/runner.py` 的 `_finish_frame` 在推理之后才写一帧，循环每处理完一帧写一帧。双路 1080p 加姿态推理时，循环只有 8～20 fps。
- `RecordingController` 却按名义帧率 `NOMINAL_CAMERA_FPS = 30.0`（`core/live/config.py`）打开 writer。
- 正侧两路在同一步里写入，所以两路仍逐帧同步，只是整体变速。

**影响**：
- 练习与考试的规则时间都由"帧号 ÷ fps"得到（`rule_checks.rule_series`），护位保持窗口、最短动作时间、最大断档、正侧时间容差全部偏离 1.5～3.7 倍。
- 帧率低还会让快速出拳、踢腿出现运动模糊，影响手脚关键点。
- 分析报告里"多数片段实战式保持不足"的结论可能是变速造成的，需要在修复后复核。

**方案**（实现时三选一，优先第一种）：
1. 按墙钟时间补帧或丢帧，使文件是真正的 30 fps 恒定帧率：每次写入时按距开录的时间计算应写到第几帧，不足则重复上一帧，超前则跳过。
2. 录像直接取采集进程的帧，与推理解耦，推理慢不影响录像。
3. 记录每帧的真实时间戳，在 finalizer 的 ffmpeg 转码步骤中按时间戳重定时。

无论哪种方案，片段目录、文件名和 `result.json` 结构都不变。

**验证**：
- 用假的慢速流水线写单元测试：修复前失败，修复后视频时长等于墙钟时长（误差 < 3%），正侧帧数相同。
- 实机上用练习模式拍 60 秒秒表，回放时长一致。
- 冻结 EXE 跑 `--offline-self-check`。

**范围外**：规则参数不在此步改动。

> 已在单独的会话中提出这一项（"Fix recorded videos playing back too fast"），批准后实施。

### 步骤 1：样本评估工具入库（不改行为）

**目的**：把这次分析用的一次性脚本（`outputs/sample_analysis/scripts/`）整理成 `analysis/` 下的正式工具，让步骤 3～6 的每个 PR 都用同一套指标对比修改前后。

**内容**：

- **指标**：
  - 每个检查项在正确样本上的逐视角误报率与融合误报率；
  - 在对应错误样本上的检出率；
  - 动作阶段检出率；
  - 正侧对齐失败率。
- **报告**：生成固定格式的 Markdown 对比表，作为后续规则 PR 的必附材料。
- **样本清单**：新建 `docs/样本清单.md`，登记样本根目录与批次，取代 `docs/yolo_eval_samples.json`（D-11 遗留项）。
- **入库要求**：遵守仓库规则（模块 docstring、体量上限、架构测试），只调用 `core` 各包的公共 API，不进入生产路径。

**验证**：在第一批样本上复现报告第四节的数字。

### 步骤 2：侧面机位改到考生右侧并重拍（D-19）

**现象**：侧面摄像头在考生左后方，斜着拍。左式时考生胸口朝右、后背朝左，所以侧面拍到的主要是后背，右手（护脸的后手）和右腿几乎看不到。

**方案**（甲方配合）：
- **位置**：侧面摄像头移到考生右侧，与正面摄像头的拍摄方向成 90°，正对考生身体侧面，而不是在身后斜拍。高度约在胸口，距离以全身占画面高度约七成为准，避开立式空调。
- **考场一致**：考场的机位必须同样调整，否则样本和实际考试不一致。
- **侧面模板重录**：机位换边后，侧面画面中人物朝向相反，现有的侧面模板（`pose33_v3`）不能再用于新机位，需要用新机位重录教师示范。正面模板不受影响。
- **重拍样本**：在步骤 0 的修复版本上，按 `docs/样本视频采集清单.md` 重拍，并交标注表（人员编号、动作、故意做错的项、逐项教师判定）。C 类每项至少 2 人，并补正确对照。

**代码影响**：
- 规则里与朝向有关的测量（向后拉手、翻胯）都按起始护位自动判断方向，不依赖机位在哪一侧。
- 落地前需在新机位样本上复核 `PRIMARY_VIEW` 与各检查项的正侧权重（`default_front_weights`）。
- 若有考生用右式，新机位会重新拍到后背。目前考试固定左式（`DEFAULT_STANCE`），暂不处理。

### 步骤 3：融合允许单视角结论，动作按峰值时间配对（D-20）

**现象**：`core/evaluation/practice.py` 的 `_fuse` 只有同时满足以下条件才给结论，否则一律"证据不足"：
1. 两个视角都找到该阶段（第 105 行）；
2. 正侧对齐可靠（第 109 行）；
3. 每个基础权重 > 0 的视角都有测量结果（第 118 行）。

另外，`phases.align_views` 只要任何一个动作段的正侧次数不同（第 159 行），就把整段对齐判为不可靠，连实战式检查也一并变成"证据不足"。

**方案**：
1. **单视角结论**：
   - 一个视角缺阶段或缺关键点时，另一视角若有足够有效帧（`valid_ratio`、`min_valid`），就只用这一视角判定。
   - 状态仍用 `candidate` / `not_observed`，`fusion.method` 记为 `single_view`，原因写明"仅侧面（或正面）可见，请教师复核"。
   - 只有两个视角都没有可用证据时才是 `unable`。
   - 单视角判定是否需要更高的触发比例（例如 `trigger_ratio` 提高到 0.5），在步骤 1 的指标上比较后决定。
2. **按峰值时间配对**：`align_views` 改为把正侧 finish 峰值按时间最近配对：
   - 时间差在 `phase_tolerance_seconds` 内的算一对，用配对结果估计偏移；
   - 配不上的动作只在本视角判定，不影响已配对的动作和其它检查项；
   - 至少配上 1 对即可估计偏移；配上 2 对以上时，沿用现有的残差检查。
3. **实战式不依赖动作配对**：`stance:start`、`stance:end` 的检查项单独比对两个视角的护位窗口时间，不受动作次数不一致影响。
4. **结果字典**：`schemaVersion` 保持 1，只新增 `fusion.method` 的取值和 `alignment.pairs`（配对明细）。历史记录的读取与报告渲染要兼容新取值。

**涉及模块**：`core/evaluation/practice.py`（`_fuse`、`_evaluate_check`）、`core/evaluation/phases.py`（`align_views`、`share_phase_timing`）。结果页与 HTML 报告对 `single_view` 的文案在 `core/reporting/` 与 `apps/tk/views/practice_result/`。

**测试**：
- 新增用例：单视角缺阶段、鞭腿正侧次数不同、实战式不受动作配对影响。
- `test_action_feedback.py`、`test_p3_eval_differential.py` 中受影响的期望值按决策重新生成，PR 中逐条列出变化（D-13）。

**验证**：在第一批样本上，报告中 7 对 view_only（C15 t1/t2、C17、C18 t1、C20 等）应变为有结论；同时 A、B 正确样本的误报率不能因此明显上升，用步骤 1 的报告对比。

### 步骤 4：识别"打出后保持"的动作（D-23）

**现象**：`phases._segment_events` 要求手（或脚）离开起始护位超过 `motion_distance`（0.25 躯干长）后，再回到 `return_distance`（0.15）以内，才算一个完整动作。

C 类的静态演示是打出后停住，再换护位，离起始护位最近也有 0.19～0.43，因此一直找不到动作。`return_distance` 不能单独放宽：它必须小于 `motion_distance`，试算放宽到 0.20 也几乎没有变化。

**方案**：
1. **以静止判定动作结束**：离开护位后，若移动点的速度连续 `hold_seconds`（新参数，建议 0.3 秒）低于阈值，就判定动作结束，峰值取停住的位置。之后无论是否回到护位，都开始寻找下一个动作。
2. **以结束护位作参照**：没有回到起始护位，但最后能找到稳定护位时，以结束护位作第二参照判断"已回收"。
3. **两种结束方式都要记录**：在 diagnostics 中写明本次动作按"回到护位"还是"静止"结束，供教师核对。
4. **先问教师**：真实考生是否会"打出后保持"。如果不会，第 1 点只作为容错，拍摄要求仍写"每拳回到护位"。

**依赖**：所有时间参数都按秒计，必须在步骤 0 之后、用真实时间的样本调。

**测试**：合成序列覆盖以下情形：
- 打出后停住；
- 打出后回到护位；
- 打出后换到别的护位；
- 连续两拳中间不回护位。

**验证**：在第一批样本上，C 类单拳的阶段检出率从 10/21 明显提高，B 类组合拳的"次数或顺序不完整"不增加。

### 步骤 5：改用三维世界坐标与正确的参照点（D-21）

**现象与原因**：
- 规则用的是图像平面上的二维坐标（宽高比修正后），但教练标准说的是身体的真实角度和距离。机位一斜，二维角度和距离就会被压缩或拉伸：
  - **前手肘角**：正面看，护手指向镜头，肘角被压扁，正确样本中位数只有 27°（标准 90°～135°）。
  - **膝角**：膝盖向前屈，正面看几乎是直的，于是被判"腿伸直"。
  - **站距**：左式两脚前后站，正面看横向距离很小，于是被判"过窄"。
  - **脚尖方向、勾脚尖**：脚部点在正面被透视压缩，MediaPipe 的脚尖点也不稳定。
- 参照点也有误："拳峰高度"实际量的是手腕，并取绝对值。
- MediaPipe 本身会输出三维世界坐标（米，以髋部中点为原点），但 `core/pose/engine.py` 第 244 行只保留了图像坐标 `pose_landmarks`，`pose_world_landmarks` 被丢弃。

**方案**：
1. **保留世界坐标**：
   - 引擎在 `infer()` 之外另提供一个返回世界坐标的接口。`infer()`/`annotate()` 的语义不变（硬约束），`pose33_v3` 模板与 golden 也不变。
   - `PoseSequence` 增加可选的 `world` 数组，缺失帧为 NaN，有效性仍只由 `derive_valid_mask` 判定。
2. **规则序列带上世界坐标**：`rule_series` 增加 `world`；离线、练习、考试三条路径都传入。
3. **逐项改用合适的测量**：

   | 检查项 | 新测量 |
   |---|---|
   | `stance_elbow`、`punch_extension`、`stance_knee` | 世界坐标中的三维关节角 |
   | `stance_width` | 世界坐标中两踝的水平距离 ÷ 三维肩宽；"前后站"和"左右站"可以分开量 |
   | `stance_height` | 拳峰改用食指根、小指根（BlazePose 17～20）的中点，带符号的纵向差（拳高于还是低于鼻尖） |
   | `stance_toes`、`foot_flexed` | 先在步骤 1 的样本上验证世界坐标中脚部点的稳定性；不达标就保持暂停（见步骤 6） |
   | `stance_torso` | 世界坐标中肩线与正面相机方向的夹角 |

4. **两个视角的三维结果应当接近**：融合时可以检查两者是否一致，不一致说明有一路关键点不可靠，降低其权重。

**范围**：这是改动面最大的一步。涉及 `core/pose/engine.py`、`core/pose/sequence.py`、`core/pose/extract.py`、`core/evaluation/rule_checks.py`、`core/evaluation/measures/`、`core/evaluation/rules/sanda_v5.py`，以及练习历史中的测量值单位。建议分两个 PR：
- **5a**：保留世界坐标，不改任何规则，输出零漂移；
- **5b**：逐项切换测量，规则版本升为 v6。

**测试**：
- 5a 要求 golden、契约测试零漂移。
- 5b 新增已知三维姿态的合成用例；`test_action_feedback.py` 等按决策重新生成。

**验证**：在第一批样本上，`stance_elbow`、`stance_height`、`stance_knee`、`stance_width` 的正确样本误报率显著下降，C1～C8 的检出方向正确（如 C1 应报"过直"而不是"过弯"）。

### 步骤 6：按教师确认的正确样本标定阈值（D-22）

**现状**：`FeedbackConfig` 的阈值都是"工程初值、暂定"，从未在真实样本上标定过。

**6a 立即止损**（只依赖步骤 1，可先做）：
- 把在正确样本上逐视角误报率 ≥ 50% 的检查项暂时改为 `pending_rule`（结论显示"待规则/测量确认"），直到步骤 5 和 6b 完成。
- 按第一批样本，涉及 `stance_elbow`、`stance_height`、`stance_toes`、`foot_flexed`，以及 `stance_width` 的下限。
- 这样学生不会再看到大量错误提示。

**6b 标定**（依赖步骤 2 的重拍样本和步骤 5）：
- 每个检查项用教师判定为"对"的样本的测量值分布定阈值，例如取正确样本的第 95 百分位，使误报率 ≤ 5%～10%。
- 用对应的错误样本检验检出率；检出率不达标的项不上线，保持 `pending_rule`。
- 结果写成标定报告（样本数、分布、阈值、误报率、检出率），随 PR 提交。阈值写进 `FeedbackConfig` 默认值，现场仍可用 `feedback_config.json` 覆盖。
- 正侧权重（`default_front_weights`）同样按样本上各视角的可靠性重新标定。

**上线标准**（建议，待用户确认）：一个检查项在正确样本上的融合误报率 ≤ 10%，在对应错误样本上的检出率 ≥ 70%，且至少有 2 名执行者的错误样本。不达标就保持 `pending_rule`。

## 四、每个规则 PR 都要附的材料

1. 对应的决策项编号与批准记录（设计文档 §11.2）。
2. 步骤 1 工具生成的修改前后对比报告：每个检查项的误报率、检出率、阶段检出率和对齐失败率。
3. 受影响的 golden 与测试期望值清单（D-13）。
4. 规则版本号是否升级。改变结论或测量的 PR 都要升级 `RULE_VERSION`，练习历史中的旧记录保持原样显示。

## 五、不在本计划内

- `stance_head`（含胸收腹）、`vertical_fist`（立拳）：Pose33 无法可靠判定，维持 `pending_rule`，见缺失规则的 issue。
- body_core 标定（D-11，issue #23）：等步骤 2 的重拍样本。
- YOLO 不进入任何规则评分（硬约束不变）。
