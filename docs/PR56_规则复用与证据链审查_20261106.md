**PR #56：规则复用、动作计次与证据配图审查（2026-11-06）**

跟踪 Issue：[#57](https://github.com/gy212/vision-refactor/issues/57)，包含完整上下文、可运行复现脚本、前后对照证据与10项修复验收清单。缺陷尚未修复。

结论：共用规则引擎已经存在，但检查项的业务定义没有统一。相同检查项编码在不同整套动作下，使用不同的视角、公式、阈值和启用状态。#56 沿用并扩大了这一分叉；报告还存在与判定依据脱节的证据选择。不能把这些问题解释为“每套动作理应各自维护规则”。

审查对象是 [PR #56](https://github.com/gy212/vision-refactor/pull/56) 的最终提交 `30286e75647b78ace848a53a885ed20aa6153bdf`，已于 2026-11-06 合入。GitHub API 已核对 PR 说明、两个提交、25 个变更文件及合并状态。对照使用 #54 的 `d462431cd6c2e8b1e081af5ecb6ef7f9e8eaa5e2`，其 Git 文件树与 #56 实际合并基线 `7eff6a96a1dae05d30735013255a1383cdc993ed` 相同。复现运行于独立的现有 worktree，未把主工作区的未提交代码当成 PR 内容。

用户提供的 `outputs/3_后手直拳_练习分析报告.html` 为后手直拳、v5.10、记录 `c9c6f56fbdc14badb39305f39705634b`。报告共有 30 项：1 项疑似问题、2 项未发现问题、19 项无法判断、8 项未自动检查。截图首项为前手肘角，指定 HTML 首项为站距，二者不能直接视为同一份结果。本次对截图对应的选图机制独立复现。

**1. [P1] 同一检查项随整套动作切换定义；#56 新增公式分支并扩大既有分叉。**

入口仍是同一个 `rule_profile()` / `evaluate_rules()`，但 `SIDE_TIMED_ACTIONS` 只包含 `step_straight_combo`。这个原本表示侧面分段方式的集合，被同时用来选择检查清单、规则公式、关键点、阈值和资格登记。

直接位置：[sanda_v5.py 的公式分派](https://github.com/gy212/vision-refactor/blob/30286e75647b78ace848a53a885ed20aa6153bdf/core/evaluation/rules/sanda_v5.py#L646)、[关键点分派](https://github.com/gy212/vision-refactor/blob/30286e75647b78ace848a53a885ed20aa6153bdf/core/evaluation/rules/sanda_v5.py#L688)。#56 在前者加入伸直、脚向、站姿高度、贴身距离等分支，并引入后者。

实际通过规则目录读取到的差异：

| 相同检查项 | 上步前后手直拳组合 | 单独后手直拳／普通直拳组合 |
|---|---|---|
| `stance:start:front:stance_elbow` | 仅侧面；80°～135°；试用 | 正面20%＋侧面80%；90°～135°；没有资格字段 |
| `stance:start:front:stance_height` | 正面；手腕与肩比高低 | 双面；手腕与鼻尖比高低 |
| `stance:start::stance_width` | 脚尖或脚跟间距，参照双面肩宽 | 踝距，参照单面投影肩宽 |
| `stance:start::stance_toes` | 两脚尖间距减两脚跟间距 | 两个脚向量的夹角 |
| `rear_straight:finish:rear:punch_extension` | 侧面；177°；每次窗内是否曾伸直 | 正面40%＋侧面60%；160°；逐帧问题比例 |

同一输入、同一检查项编码、同一阶段的确定性复现：侧面肘角固定约 85°，上步组合得到 `pass`，单独后手直拳、普通组合、单独实战式均得到 `violation`。另一组同样的手腕坐标，上步组合检查“腕与肩”得到 `pass`，其余动作检查“腕与鼻”得到 `violation`。这验证了执行结果分叉，并非仅报告文字不一致；合成输入不用于证明真实识别准确率。

历史归因：动作名单分支在 #56 之前已有。#56 新增 `PREFERRED_VIEW`、新的测量函数和容错后，继续只从上步组合进入，扩大了相同编码的不同含义。PR 说明明确写了“容错仅用于上步直拳”；80°、175°、15°及开启试用有既有决策记录，本审查不把这些数字或试用决定本身判成擅改。工程问题是将差异隐藏在整套动作分支里，缺少独立、可审计的检查项策略。

仓库规范在该 PR 当时已要求“每项能力只留一个实现”“差异改写为命名策略”“不要复制一份旧代码再改”，见 [当时的 AGENTS.md](https://github.com/gy212/vision-refactor/blob/30286e75647b78ace848a53a885ed20aa6153bdf/AGENTS.md#L22)。这不是后来新增规范才暴露的问题。

**2. [P2] 资格登记同时改规则定义，测量与展示各自维护身体部位。**

`apply_straight_availability()` 名义上登记资格，实际还删除检查项、改名称、改标准、改来源、决定主视角；#56 新增了大量此类副作用。位置：[straight_policy.py](https://github.com/gy212/vision-refactor/blob/30286e75647b78ace848a53a885ed20aa6153bdf/core/evaluation/rules/straight_policy.py#L126)。资格验证范围因模型、阶段或样本而不同是合理的；是否有资格不应隐式决定一条规则究竟量什么。

与此同时，规则所需点由 `required_landmarks()` / `_required_for_action()` 声明，报告高亮却由独立的 `RULE_JOINTS` 按短代码选择。`stance_elbow` 测量左式前手只需左肩、左肘、左腕，配图会把两条手臂六个点一起标红；本次截帧调用已记录这一结果。`punch_extension`、`guard_shoulder` 在该高亮表中没有对应项。高亮表问题原已存在，#56 更改测量点及含义时没有同步这份独立定义。

影响：后续修改一个检查项，必须同时记得修改清单、资格函数、公式分派、取点分派和报告高亮表；任一处遗漏，就出现名称、实际判法和配图指示的身体部位不同步。

**3. [P2] #56 新增提醒合并后，结束阶段截图被截掉。**

新增的 [issue_groups.py](https://github.com/gy212/vision-refactor/blob/30286e75647b78ace848a53a885ed20aa6153bdf/core/reporting/issue_groups.py#L32) 把过程与结束合成一条 `NormalizedCheck`，只拼接 `phase_label`、说明和证据列表；结构中的 `phase`、`id` 仍来自第一项。下游 [renderer.py](https://github.com/gy212/vision-refactor/blob/30286e75647b78ace848a53a885ed20aa6153bdf/core/reporting/html/renderer.py#L145) 继续只取证据列表前两张。

复现输入：过程证据为第 10、11、12 帧，结束证据为第 20、21、22 帧，两阶段均提示同类抬肘问题。

- PR 基线：两张卡片，实际请求 10、11、20、21 帧，两个阶段都有图。
- #56：一张卡片写“动作过程、动作结束瞬间”，实际只请求 10、11 帧，结束阶段没有图。

现有新增测试只验证合并后的列表保留引用及卡片数为 1，没有验证真正展示了哪些阶段的截图。这是 #56 新引入且可复现的行为回归。应保留各阶段的结构化成员，再按成员选代表帧；不应将不同阶段压成一条失去来源的扁平引用列表。

**4. [P1，既存] 两张配图全是正面的直接原因已经复现。**

`practice.py` 按正面、侧面的顺序处理测量；每个视角的证据为首、中、末三帧；`adapters.py` 顺序追加证据；HTML 直接切 `[:2]`。该选择不读取视角权重、哪一面判出了问题、规则要求的观察方向。

本次经公开 `evaluate_series()`、`render_html_report()` 入口复现的前手肘角候选项：

```text
基础权重：front=0.2，side=0.8
保存引用：front:51, front:54, front:57, side:51, side:54, side:57
真正请求截图：front:51, front:54
```

截图解码在复现中替换成固定小图，只记录渲染器实际请求的视角、帧号和高亮点；规则计算与选证据逻辑使用真实代码。基线与 #56 结果相同，因此不能把这一旧问题说成 #56 新写坏的。但 #56 的选面修复只覆盖了上步组合的规则配置，没有解决通用报告选择证据的问题。

另一个语义问题是：两面都留了观测证据，报告未区分“支持问题的画面”和“仅供对照的画面”。按插入顺序取图，甚至可能展示未观察到问题的一面，隐藏真正支持结论的一面。

**5. [P1，既存] 通用计次不区分位移方向；全局对齐失败传播到无关站姿检查。**

普通后手直拳进入 `phases.py`，两路分别按腕相对肩的二维距离离开护位、再返回护位检测事件。该信号把向前、向下等位移都压成距离。正面和侧面的二维投影、遮挡及点位缺失会产生不同事件边界或漏检；没有保证两路独立检测能得到同一次动作列表。

确定性复现：合成序列只让右手向下放再回护位，没有任何向前出拳，两路仍各认出一次 `rear_straight`。这一结果在基线和 #56 均存在，证明通用事件检测有把非出拳动作计成拳的路径；不能据此断言用户原录像正好发生了这一种误检。

`align_views()` 比较两面结束窗口的连续段数，只要不同，便将全局 `alignment.reliable` 设为 `False`。`_fuse()` 随后对所有仍需两面融合的检查项重复使用这个失败原因，连开始实战式的肘角、膝角也一起无法判断。#56 已解除单面项的全局对齐依赖，这部分改动有效；但同名肘角等项目在后手直拳仍被配置为双面，问题继续保留。

用户指定 HTML 的 19 项“无法判断”实际分为：

| 原因 | 项数 |
|---|---:|
| 正侧面检测到的动作次数不一致 | 10 |
| 侧面护手测量有效帧不足 | 2 |
| 正面未找到结束实战式 | 7 |

所以“次数不一致”重复十次，是同一个全局失败原因影响十条规则。报告没有显示两路各自检测到几次，本次也未找到该记录 ID 对应的完整历史 JSON 与原录像，不能给出原录像哪一路多算、哪一路漏算的结论。所做的两次对一次合成复现只证明状态传播机制。

**测试为什么没挡住。**

本次在 #56 最终提交运行 `tests/test_straight_refinements.py` 和 `tests/test_architecture.py`，36 项通过。架构测试检查导入分层、循环、相似代码、模块体量等，并没有表达“同一业务检查项跨动作复用”的语义约束；没有跨层 import 违规不代表规则定义统一。

新增测试还显式断言其他动作保留旧参数，见 [test_straight_refinements.py](https://github.com/gy212/vision-refactor/blob/30286e75647b78ace848a53a885ed20aa6153bdf/tests/test_straight_refinements.py#L297)。这些用例保护了局部修改范围，却没有验证共用检查项是否仍是一致的业务能力。其“合并证据保留”用例也只检查中间结构，未检查导出图片。

逐次伸直被总有效帧比例稀释的问题已在 #56 的说明中列为已知限制，本次不重新包装成新发现。已修复的文本试用标记问题也不列作当前缺陷。

**修正应从职责边界入手。**

1. 动作编排负责动作顺序、阶段边界和引用哪些检查项；共用检查项统一持有测量、所需点、视角、参数含义和证据部位。确有不同技术标准时使用明确命名的策略，不能只靠整套动作名暗中换公式。
2. 资格登记单独描述某个策略在某模型、阶段、拍摄条件下的验证状态，不修改检查项语义；复用实现也不等于跨模型、阶段继承验证资格。
3. 事件检测、两路时间映射、单项规则判断分别产出状态。单面即可判断的站姿项目只依赖自己的有效证据，双面联合项目才依赖对应关系。
4. 证据按检查项、阶段、视角、实际测量部位传给报告；先选能支持结论的代表帧，跨阶段合并仍保留成员来源，再应用图片数量限制。
5. 增加跨动作同规则契约和最终 HTML 图片选择验证，使用同一输入核对实际结果，避免只核对配置与中间列表。

不能将其他动作直接加入 `SIDE_TIMED_ACTIONS` 作为修复：这会同时触发上步前后手组合的专用切分和考试逐次评分，单独后手直拳反而会被要求出现前后手组合。应先拆开计时策略与规则策略的绑定。
