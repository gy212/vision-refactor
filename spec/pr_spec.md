# PR 描述规范（架构破立交底与实证准则）

本规范旨在根除 Agent 在编写 PR 描述时的五大恶习：**标题含糊或堆砌细碎动作**、**“报喜不报忧”美化半拉子工程**（把未接通的遗留分叉包装成“合理兼容”）、**行文晦涩或偷工减料漏掉关键交底小节**、**用“测试通过数字注水”代替“真实业务结果前后对比”**、以及**在结尾堆砌大段防御性免责声明**。

---

## 1. 核心定位：PR 描述是“诚信交底书”，不是“表功公关文”

PR 描述必须让人类审阅者在 **15 秒内** 看清三个核心事实：**做法到底对不对？旧烂路径删干净没有？改前改后真实输出变了什么？**

1. **破立透明（拒绝暗藏双轨）**：建了什么新公共能力，就必须明确交底接通了哪些消费方、删掉了哪条旧路径。**凡是有同类场景未接入或保留了特殊分支，必须在交底表中白纸黑字列出，严禁用“保留既有差异”、“维持兼容”等模糊话术蒙混过关。**
2. **实证对比优先（拒绝测试数字通胀）**：严禁靠罗列“77 项通过、149 项通过”充门面。必须用一张直观的对比表，展示**触发场景与兄弟场景在修改前（base）与修改后（PR）的实际结果变化**。
3. **语言简洁易懂，内容完整不丢小节**：
   - **简洁易懂（说人话）**：全程用通顺、直白的大白话把“改了哪、为什么这么改、效果如何”讲清楚，拒绝生造伪学术概念、拒绝绕口长句、拒绝把代码 Diff 逐行翻译成文字流水账。
   - **完整不丢小节（严禁偷工减料）**：下方 §4 模板中的**所有小节与表格行均属强制必填结构**，严禁擅自删减、合并或跳过任何一节；即使某一项为“无”（如未保留任何特判差异、无替换旧测试），也必须保留该小节/表项并显式写明“无”，确保交底信息 100% 完整闭环。

---

## 2. PR 标题撰写规范（强制格式）

PR 标题将永久进入 Git 主干历史（`git log --oneline`），必须简洁、准确、一目了然：

- **标准格式**：`<type>(<scope>): <用简洁动宾短语点明核心破立结果>`（分阶段 PR 在末尾加 `（#Issue号, k/N）`）
  - `<type>` 严格限定：`feat` / `fix` / `refactor` / `docs` / `test` / `chore`
  - `<scope>` 填写核心受影响的包或领域名（如 `evaluation`、`rules`、`reporting`、`pose`、`tk`、`exam`）
- **三条硬约束**：
  1. **写“根治了什么本质”，不写“修了哪个样本”或“改了哪个函数”**：
     - ❌ 错误示例：`fix: 修复后手直拳报告有效帧不足并调整 punch_events 与 step_reps`（样本表象 + 文件名堆砌）
     - ✅ 正确示例：`fix(evaluation): 统一单拳与组合直拳规则标准并展示无法判断现场证据`
  2. **简洁直白（控制在 35 字以内）**：用一句主干清晰的动宾短语概括，禁止用两三个逗号把多个琐碎动作拼成冗长长句。
  3. **名实相符（严禁夸大）**：如果只改了底层函数而未接通全部消费方，标题严禁写“统一/全量接通”，必须如实反映实际交付范围。

---

## 3. 正文写作四条铁律（严禁触犯）

1. **严禁丢小节或砍表项**：正文必须完整包含 §4 模板的 **顶部核心摘要 + 1. 架构破立交底表 + 2. 核心业务结果前后对比 + 3. 验证命令与测试变更说明** 四大部分，小节标题与表格行一个都不准少。
2. **严禁隐瞒特判或未闭环分支**：只要代码中存在针对特定场景的条件分支或未迁移的旧路径，必须在【架构破立交底表】的“保留差异 / 未覆盖项”中如实招供并解释原因，隐瞒不报视为严重失信。
3. **严禁堆砌测试计数与免责套话**：不准写“某测试 77 项通过、某套件 56 项通过、数字有交叉不相加、不代表全量准确率验收、未构建 EXE”这类充门面和防追责的废话；非真实阻塞的免责声明一律清零。
4. **被替换的旧测试必须显式交底**：若删除或修改了既有测试断言，必须在第 3 节明确说明“原断言为什么错（是否属于保护错误分叉的毒药测试） → 新断言验证什么真实业务语义”。

---

## 4. 强制输出模板（严格按此结构编写，小节一个不准少）

```markdown
## 核心摘要

> - **关联任务**：Closes #<Issue编号>（或关联 #<编号>，无则填“无”）
> - **一句话交底**：（用通顺大白话说明：本次在哪个公共层根治了什么问题，接通了哪些同类场景，淘汰了什么旧路径。）
> - **闭环状态**：🟢 **全量闭环（所有同类场景已接通且旧路径已移除）** / 🟡 **分阶段交付（存在显式保留边界，见下表）**

---

## 1. 架构破立交底表（四行必填，严禁删行或模糊表述）

| 交底维度 | 本次 PR 实际落地情况（用大白话如实填写） |
| :--- | :--- |
| **源头根治位置** | 说明核心逻辑修改在哪一层、哪个公共模块，如何从源头解决问题（而非下游擦屁股） |
| **已接通的同级场景** | 明确列出本次统一接通生效的所有动作 / 业务入口清单 |
| **已删除的旧路径** | 明确列出本次彻底移除的旧函数、旧分叉、重复计算或过渡配置（若无旧路径可删，写明原因） |
| **保留差异 / 未覆盖项**<br>*(诚信红线：无则填“无”)* | 若有任何同类场景未接入、或保留了特殊条件分支，**必须在此逐一列出并说明原因**；严禁暗藏在代码中不报 |

---

## 2. 核心业务结果前后对比（改前 base vs 改后 PR）

| 验证场景（必须包含触发场景与兄弟场景） | 修改前（base）实际结果 | 修改后（PR）实际结果 |
| :--- | :--- | :--- |
| **触发场景**：<具体输入/案例> | <改前的错误表现/关键数值> | <改后的正确表现/关键数值> |
| **兄弟场景**：<同类动作/入口输入> | <改前的表现/关键数值> | <改后的表现/关键数值> |
| **边界/异常场景**：<缺帧/遮挡等边界输入> | <改前的表现/关键数值> | <改后的表现/关键数值> |

---

## 3. 验证命令与测试变更说明

- **核心新增/更新测试**：
  - `<test_file.py>`：用一句话说明验证了什么跨场景业务闭环或契约。
- **被替换/修改的旧测试交底**（无则保留本项并填“无”）：
  - 原 `<test_old>` → 现 `<test_new>`：说明原断言为何不合理（如：保护了错误的局部特判），新断言如何对齐真实业务。
- **最小可复现验证命令**：
  ```powershell
  .\.venv\Scripts\python.exe -m pytest <直接受影响的核心测试文件> -q
  ```
```
