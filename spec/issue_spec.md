# Issue 编写规范（根因定义与作用域锁定准则）

本规范旨在根除 Agent 在编写 Issue 时的四大顽疾：**标题含糊或把“单一触发样本”当成“问题全集”**（诱导接手者写出局部特判补丁）、**把“下游表面症状”当成“问题根因”**（诱导接手者在消费端擦屁股）、**行文晦涩绕口或偷工减料漏掉关键小节**、以及**堆砌几十 KB 的排查流水账与免责废话**。

---

## 1. 核心定位：Issue 是“工程破立契约”，不是“现象备忘录”

1. **从“触发样本”向上抽象一层**：用户报错的具体文件、动作或入口只是**暴露问题的观测窗口**。必须在 Issue 中直接点破它背后的**公共概念层缺陷**，并明确列出所有共享同一病根的**同级兄弟场景**。
2. **锁定源头，拒绝下游打补丁**：必须指明问题产生的**唯一事实源头**，明确要求在源头根治并淘汰旧残缺路径，从任务定义阶段就封死接手者“加特判分支”或“留 `legacy` 双轨”的退路。
3. **语言简洁易懂，内容完整不丢小节**：
   - **简洁易懂（默认简中，保留专业术语）**：默认统一使用**简体中文**（仅保留必要的英文专业术语、代码符号与模块路径），全程使用直白、通顺的大白话，主谓宾清晰，让人类在 **10 秒内** 看懂“哪坏了、为什么坏、要改哪一层、影响谁、怎样算修好”。严禁全英文撰写、严禁堆砌晦涩的伪学术黑话、严禁绕口长难句、严禁贴几十 KB 的排查日志充字数（复现脚本与长日志一律折叠进底部 `<details>`）。
   - **完整不丢小节（严禁偷工减料）**：下方 §4 模板中的**所有小节与表格列均属强制必填项**，严禁擅自删减、合并或跳过任何小节；每个问题点必须完整交底“表面现象、源头代码位置、失灵原因、兄弟场景范围与改前改后对照”，不得遗漏关键细节。

---

## 2. Issue 标题撰写规范（强制格式）

Issue 标题是人类和下游 Agent 的第一锚点，严禁写成病句拼盘或单样本流水账：

- **标准格式**：`[<类型>][<所属模块/领域>] <一句话点破公共机制缺陷或核心诉求>`
  - `<类型>`：`Bug`（缺陷） / `Refactor`（架构或公共复用整改） / `Feat`（新功能） / `Perf`（性能）
  - `<所属模块/领域>`：定位到问题根因所在的包或子域（如 `evaluation/rules`、`evaluation/timing`、`reporting`、`pose`、`tk`）
- **三条硬约束**：
  1. **主语必须是“公共机制”，严禁是“触发样本”**：
     - ❌ 错误示例：`3_后手直拳报告里前手肘角判法不对，而且重复报10条次数不符、配图只有正面`（现象拼盘 + 锚定单样本）
     - ✅ 正确示例：`[Bug][evaluation/rules] 同类直拳规则判法未统一且报告配图未按主判定机位选取`
  2. **一题一主线，拒绝逗号拼盘**：标题控制在 **35 字以内**，提炼背后的唯一本质矛盾，禁止把三四个下游表象用逗号硬拼在一起。
  3. **直白易懂**：禁止在标题里堆砌私有函数名或晦涩缩写，必须让人一眼看懂问题性质与影响域。

---

## 3. 正文写作四条铁律（严禁触犯）

1. **严禁丟小节或省细节**：正文必须严格包含 §4 模板的全部 **4 个核心小节 + 顶部摘要栏**。若某栏确无内容（如“关联上下文：无”），也必须保留该项并显式写“无”，严禁擅自砍掉章节。
2. **严禁写晦涩绕口的“机器腔”**：把“选源器与实际识别的输入契约不一致”写成“选机位时没检查识别必需的鼻点参照，导致选了缺鼻点的侧面后识别直接退出”——必须把因果链条用最直白的话讲透。
3. **严禁罗列细碎的补丁式 Checklist**：验收清单（Done Criteria）控制在 **3～5 条**，严格按“源头根治 → 同级接通 → 旧路径清理 → 核心验证”组织，严禁碎成十几条表面修补项。
4. **严禁堆砌防御性免责话术**：正文中只写真实阻塞与明确边界，严禁塞入“跑了多少无关门禁”、“某提交前已存在所以不算新回归”等推诿废话。

---
